# レールをつなごう！ゲーム 設計書

## 概要

3歳児向けの静的ブラウザゲームとして、欠けた線路に正しいレールピースを置き、自動で走る電車をゴール駅まで導く。サーバーは使わず、GitHub Pages で公開できる構成にする。

世界観は「絵本の旅」。空、森、虹、川辺、夜空など、やさしい場面変化の中で電車が進む。失敗時も責める表現を避け、短いリトライで遊び直せる体験にする。

## 体験設計

プレイヤーは最初に電車を選び、選んだ電車のコースを遊ぶ。各電車には5コースがあり、最初は難易度1のみ遊べる。コースをクリアすると、同じ電車の次コースが解放される。別の電車はいつでも選べる。

ゲーム中、電車は線路上を自動で進む。画面上には欠損した線路が複数同時に見える場合がある。プレイヤーは画面下部の候補欄から使い切りの線路ピースを選び、穴へ配置する。操作はタップで「候補を選ぶ、穴をタップして置く」を基本にし、ドラッグ配置も受け付ける。

ピースは使い切りだが、電車が対象の穴へ到達するまでは戻す、別の穴へ移動する、入れ替える操作ができる。電車が穴の到達ポイントに来た時点で、その穴に正しいピースが置かれていれば通過する。未配置または不正解ならリトライする。

## 画面構成

### タイトル/電車選択

3種類の電車を大きなカードで表示する。電車の名前や見た目は自由項目だが、絵本調に「そらでんしゃ」「もりでんしゃ」「にじでんしゃ」のような、色や形で識別しやすいものにする。

### コース選択

選択中の電車に紐づく5コースを表示する。未解放コースは強い禁止表現にせず、「つぎのおたのしみ」のようにやさしく表示する。クリア済みコースは再プレイできる。

### ゲーム画面

中央に上から見たコースマップと電車を表示し、下部に候補ピースを配置する。コースは絵本のプレイマットのように、線路の経路、曲がり角、駅、穴が同じ平面上で見える構成にする。候補ピースは幼児が押しやすい大きさにし、線路の形と向きが見分けられるようにする。画面上の穴は、置ける場所として枠や淡いハイライトで示す。

### クリア/リトライ画面

クリア時は駅到着の明るい演出を表示し、「もういちど」「つぎへ」「でんしゃをえらぶ」を出す。リトライ時は「もういっかい！」のような短い文言で戻し、失敗を責める音や表情は使わない。

## データ構造

実装はステージ定義駆動にする。コースや線路の正解はデータとして定義し、ゲーム画面はその定義を読み込んで描画、入力受付、判定を行う。

主な定義は次の通り。

- `TrainDefinition`: 電車ID、名前、色、見た目、表示用メタ情報
- `CourseDefinition`: コースID、電車ID、難易度、背景、線路マップ、穴、候補ピース、速度、リトライ方式
- `GapDefinition`: 穴ID、位置、必要なピースID、電車の到達順
- `PieceDefinition`: ピースID、形状、向き、候補欄での表示、使い切り状態
- `ProgressState`: クリア済みコース、解放済みコース、選択中の電車/コース

コース定義は不変データとして扱う。ゲーム中の配置状態、候補欄に残っているピース、電車の現在位置はランタイム状態として別に持つ。

## ゲームロジック

電車の進行はコース定義の経路に沿って更新する。電車が各 `GapDefinition` の到達ポイントに来たとき、対象の穴に置かれているピースを確認する。

正しい場合は電車が通過し、次の到達ポイントまたはゴールへ進む。未配置または不正解の場合はリトライに入る。難易度1〜2は直前の穴の少し手前から再開し、難易度3〜5はコース最初から再開する。

すべての到達ポイントを通過し、ゴール駅に到達したらクリアとする。クリア時は進捗を `localStorage` に保存し、次コースを解放する。

## 難易度設計

| 難易度 | 穴 | 候補 | 主な要素 | リトライ |
| --- | --- | --- | --- | --- |
| 1 | 1つ | 2つ | 直線、ゆるいカーブ中心。速度はかなり遅い | 直前復帰 |
| 2 | 最大2つ | 2〜3つ | 複数穴が同時に見え始める | 直前復帰 |
| 3 | 2〜3つ | 3つ | 向き違いのカーブを混ぜる | コース最初 |
| 4 | 3つ | 3〜4つ | 使う順番を少し考える | コース最初 |
| 5 | 3〜4つ | 4つ前後 | 分岐に見えるが正解ルートは1本 | コース最初 |

難易度を上げる軸は、優先度順に `穴の数`、`候補数`、`紛らわしい向き`、`速度` とする。速度は最後の調整要素にし、焦りすぎる体験を避ける。

## 技術構成

初期実装は `React + TypeScript + Vite` を第一候補にする。描画は DOM、CSS、SVG を中心にし、ゲームエンジンは導入しない。高頻度の物理演算やランダム生成が不要であり、静的公開とコース定義駆動に合うため。

想定ディレクトリは次の通り。

- `src/data/`: 電車、コース、ピース定義
- `src/game/`: 判定、進行、リトライ、クリア判定の純粋ロジック
- `src/components/`: 電車選択、コース選択、ゲーム画面、クリア/リトライ画面
- `src/storage/`: `localStorage` の読み書き
- `src/assets/`: 電車、背景、音、演出素材

アセット制作では、必要に応じて画像生成 Skill を使う。最初の候補は、3種類の電車、背景セット、クリア演出素材とする。生成画像を使う場合も、画面内の線路ピースや穴の判定に必要な形状はデータ定義と一致させる。

## 受け入れ条件

- GitHub Pages で静的公開でき、サーバーなしで遊べる。
- 3種類の電車を選べる。
- 各電車に5コースがあり、合計15コースが定義されている。
- 最初は難易度1のみ遊べ、クリアに応じて次コースが解放される。
- レールピースをタップまたはドラッグで穴へ置ける。
- 使い切りピースを、電車到達前なら戻す、移動する、入れ替えることができる。
- 電車到達時に正誤判定され、未配置または不正解ならリトライする。
- 難易度1〜2は直前復帰、難易度3〜5はコース最初からリトライする。
- ゴール到達でクリアになり、「もういちど」「つぎへ」「でんしゃをえらぶ」が表示される。
- 進捗が `localStorage` に保存され、再読み込み後も解放状態が残る。
- 同一コース内に、見た目が同じで内部IDだけ違う候補ピースを置かない。

## 非対象

- ユーザーアカウント
- オンラインランキング
- サーバー保存
- 課金
- ランダム生成コース
- 複数プレイヤー
- ネットワーク必須の外部API

## リスクと対策

| リスク | 対策 |
| --- | --- |
| 後半が3歳児には難しすぎる | 速度より穴数と候補数で調整し、速度は最後に上げる |
| 使い切りピースで詰まりやすい | 到達前なら戻す、移動、入れ替えを可能にする |
| 画像素材と判定ロジックがずれる | 見た目素材とゲーム判定用の線路定義を分け、コース定義を正とする |
| `localStorage` が壊れる | 読み込み時に検証し、異常値は初期進捗へ戻す |
| 小さい画面で候補欄が狭い | 代表 viewport で重なり、はみ出し、タッチ対象サイズを確認する |

## 性能目標

- 初回表示は軽量な静的アセットで開始できる。
- 主要操作はタップ後すぐ反応する。
- 低スペック端末でも電車の移動が滑らかに見える。
- アニメーションは CSS transform または軽量な SVG/DOM 更新を優先する。
- 音や画像は必要に応じて遅延読み込みし、ゲーム開始前の待ち時間を増やしすぎない。

## 検証方針

- コース定義の整合性チェックを用意する。穴、正解ピース、候補ピース、到達順の不整合を検出する。
- ゲームロジックのユニットテストで、正誤判定、使い切りピース、戻す/移動/入れ替え、リトライ方式、クリア判定を確認する。
- UI 変更時は代表 viewport を2種類以上確認し、線路、候補欄、ボタン、文言が重ならないことを確認する。
- service worker や強いキャッシュを導入する場合は、検証前に cache-busting またはキャッシュ削除を行う。
